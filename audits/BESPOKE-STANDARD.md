# Bespoke Standard (coordinating pass, Phase 1 output)

Written by the coordinating pass from audits/bespoke-audit.md at HEAD
57902e1. This pass replaces the spectacle pass's borrowed building
materials, primitives and vanilla pieces, with the mod's own bespoke
work. The SPECTACLE-STANDARD stays fully in force: its five points
(layered depth, debris, world interaction, atmosphere, lifecycle), its
numbers guidance, and its coordination rules are inherited unchanged.
What changes is what effects are MADE OF. Themes, colors, identity,
damage numbers, cooldowns, and mechanics do NOT change in this pass
unless a swap below forces a like-for-like substitution.

## Rule 1, GEOMETRY: bespoke or nothing

- No KiRenderHelper primitive draws (drawColoredBox, drawCylinder,
  drawDisc, drawSphere, drawHelix) anywhere in weapon scope. The
  primitive methods stay in KiRenderHelper for out-of-scope callers
  (Ki techniques, wish visuals); weapon renderers never call them.
- No hand-rolled regular geometry in weapon renderers: no equal-segment
  rings, fans, cones, domes, discs, or cylinders built from uniform
  loops, and no new per-renderer draw helper duplicates. The duplicated
  drawQuad / drawRotatingRing / drawGroundRing style helpers go away
  with the geometry they built.
- Weapon effect geometry is built ONLY with
  client/render/ki/BespokeGeometry.java: seeded procedural builders
  (tornRibbon, shardFan, bladeArc, displacedDome, brokenVortexBand,
  branch, crackStar, plume). Every builder takes a long seed; the same
  seed draws the same shape on every client. Seeds come from the
  entity (a synced seed field or a hash of synced state), never from
  client-side random or wall-clock time, so multiplayer agrees.
- Builders are parameterized: seed, colors, envelope, distScale.
  Segment counts still step down with LayeredRender.distScale and
  FxEnvelope.segments. Alpha still multiplies the envelope and the
  standard band alphas (core 0.85, mid 0.45, outer 0.18).
- LayeredRender.drawVortexBands and drawAnchorGlow are already bespoke
  (rebuilt on the toolkit in Phase 1, same signatures); calling them
  is compliant. LayeredRender.distScale is unchanged.
- One toolkit, no per-weapon geometry code. If a weapon needs a shape
  the toolkit lacks, that is a shared change request for the
  coordinating pass, never a private copy of a builder.

## Rule 2, PARTICLES: the mod's types only

- No vanilla ParticleTypes references anywhere in weapon scope, and no
  vanilla DustParticleOptions. All emission uses DbaParticles types.
- Type map (Phase 2 swaps call sites like for like):
  POOF -> DbaParticles.DUST_PUFF; CRIT -> DbaParticles.CRIT_SPARK;
  FLAME -> DbaParticles.FLAME; EXPLOSION and EXPLOSION_EMITTER ->
  DbaParticles.BLAST; BLOCK -> DbaParticles.BLOCK_CHUNKS (a
  BlockParticleOption carried on the mod's own registered type, so
  call sites pass the BlockState exactly as before and never name the
  vanilla type); DustParticleOptions -> DbaParticles.THEME_DUST with
  DbaDustOptions (same color and scale semantics as LayeredParticles.dust).
- New themed types available: ASH (dark drift for curse and darkness),
  WISP (slow glow for spirit and temporal), RAIN (storm system only,
  spawned by AtmosphereClient, not by weapons directly).
- LayeredParticles is already all-custom after Phase 1; its dust()
  helper returns DbaDustOptions. Callers of LayeredParticles need no
  changes except where they passed a vanilla outer type explicitly.
- All particle textures are the mod's own, generated by
  tools/gen_bespoke_textures.py. No vanilla particle texture, ever.

## Rule 3, SOUNDS: the mod's bank only

- No vanilla SoundEvents references anywhere in weapon scope. Every
  weapon sound is a DbaSounds event, synthesized procedurally by
  tools/gen_bespoke_sounds.py into the mod's own .ogg files.
- The bank is organized by use case, with theme variants where the old
  code faked a theme with a different vanilla sound. Phase 2 swaps by
  use case, keeping the same call sites, volumes, and pitches unless a
  variant reads clearly better. The mapping table lives in DbaSounds'
  class comment and in the Phase 1 report.
- Looping or repeated sounds (charge hums, flight) use the bank's
  loop-friendly events (charge_hum, flight_wind); do not reintroduce
  beacon or elytra sounds for them.
- Thunder for weapon storms comes from the atmosphere system
  (AtmosphereClient) using thunder_crack and thunder_dark, not from
  weapons and not from vanilla weather.

## Rule 4, DAMAGE: the mod's types for abilities

- Weapon ability damage (everything except the plain melee hit) uses
  the mod's own damage types via util/DbaDamage: one factory per theme
  family: ki, void, curse, darkness, hellfire, tempest, spirit,
  temporal, gravity, lava, valor, crush. Factories take the attacker
  (and a direct entity where the source is a projectile or construct).
- The damage type JSONs mirror the vanilla player_attack and magic
  shapes (exhaustion 0.1 or 0.0, scaling
  when_caused_by_living_non_player), so difficulty scaling and armor
  behavior for player-caused damage are exactly what they were. This
  pass changes the type, the death message, and nothing about the
  numbers.
- Death messages live in the lang file as
  death.attack.dragonblockarcanedba.<family> and its .player variant.
- HONEST EXCEPTION, by design: the plain melee weapon hit keeps the
  vanilla player attack source. That hit IS the game's weapon hit:
  the item's attack damage attribute, attack speed, knockback, and
  enchantment pipeline all key off it. Re-typing it would break the
  weapon as a weapon. Ability damage layered ON a melee hit (bonus
  hits, procs, marks) uses the custom types.
- The existing one-off vanilla types (lightningBolt, inWall, hotFloor)
  map to tempest, crush, and lava respectively.

## Rule 5, STORMS: weapons never touch world weather

- AtmosphereServer no longer reads or writes WeatherData. A weapon
  storm is a tracked volume (center, radius, gloom, kind, expiry)
  broadcast to nearby clients, exactly as before, with the kind now
  carried in AtmospherePayload. There is no weather to save or
  restore; expiry just ends the broadcast.
- AtmosphereClient renders the storm: custom RAIN particles inside
  the volume around the local player (density from DbaEffectsConfig),
  thunder from DbaSounds at random points in the volume for THUNDER
  kind, and the gloom grade through DbaPostFx as before. Vanilla rain,
  vanilla thunder sounds, and vanilla lightning are never involved.
- Lightning that should HIT something stays BoltEntity (seeded,
  bespoke geometry), spawned by the weapon as in the spectacle pass.
- AtmosphereServer.begin keeps its signature; weapon callers do not
  change for this rule.

## Rule 6, DEBRIS: the block model path (resolved, with evidence)

DebrisRenderer no longer uses MovingBlockRenderState or
submitMovingBlock. javap against BOTH audit jars (26.2 client, 26.3)
shows the replacement has identical signatures on both versions:
BlockModelResolver.update(BlockModelRenderState, BlockState,
BlockDisplayContext), obtained from
EntityRendererProvider.Context.getBlockModelResolver(), and
BlockModelRenderState.submit(PoseStack, SubmitNodeCollector,
packedLight, OverlayTexture.NO_OVERLAY, outlineColor), the exact
pattern vanilla's EndermanRenderer and CarriedBlockLayer use for a
block drawn inside an entity renderer. No DbaCompat shim is needed.
The documented trade: per-quad light-engine sampling at the block
position is replaced by the entity's packed light and baked model
tints, the same trade vanilla makes for carried blocks. Full evidence
is in audits/bespoke-audit.md section 5.

## Rule 7, TEXTURES: generated, owned, no vanilla

- New particle and effect textures are generated by
  tools/gen_bespoke_textures.py (kept in the repo) into
  assets/dragonblockarcanedba/textures/particle/. Procedural is the
  house style: the sound bank is generated the same way by
  tools/gen_bespoke_sounds.py.
- Weapon effects never reference a vanilla texture. (The one vanilla
  texture under client/render is a mob renderer's, out of scope.)

## Rule 8, BEST PRACTICES (binding on Phase 2)

- One shared foundation: BespokeGeometry, DbaParticles, DbaSounds,
  DbaDamage, LayeredParticles, LayeredRender, AtmosphereServer and
  AtmosphereClient. Parameterize by seed, colors, and envelope; never
  duplicate a builder, an emitter, or a sound recipe per weapon.
- Seeds are synced from the entity; shapes must be frame-stable (a
  builder re-run with the same seed and envelope draws the same
  silhouette, only alpha and scale breathe).
- Density and distance scaling from the spectacle standard keep
  working: every new emission path respects DbaEffectsConfig and
  every new builder respects distScale.
- Split source sets stay clean: common code never references client
  classes. BespokeGeometry and the particle, sound, and damage
  registries follow the existing split (renderers client side;
  DbaParticles, DbaSounds, DbaDamage common side).
- Dual version: every change must pass the javac audit on BOTH the
  26.2 and 26.3 classpaths with zero new error kinds versus the
  57902e1 baseline (132 kinds on 26.2, 141 on 26.3).
- Agents edit only their weapon's files, do not commit, and report
  per weapon as in the spectacle pass: swaps made (geometry, particle,
  sound, damage), any toolkit gap found, and an honest worse check.
  A conversion that looks worse is a fail: revert and say so.
- No em dashes in code, comments, reports, or commit messages.
