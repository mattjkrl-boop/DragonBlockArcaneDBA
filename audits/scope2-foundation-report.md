# Scope 2 Foundation Report (bespoke scope expansion, Phase 1 coordinating pass)

Measured and built at HEAD 8058771 on top of audits/bespoke-scope2-audit.md and
audits/BESPOKE-STANDARD.md. This pass builds only the foundation the Phase 2
fan-out is blocked on, plus the audit's named central micro-fixes. It does not
convert any Phase 2 area's own files. Carter's standing direction governs every
decision below: everything vanilla gets converted, new blocks, entities,
particles, and sounds may be created where they honestly serve, and he is not
consulted mid-pass. Verification is the javac audit only; no Gradle build ran
or is claimed (the compile check is waived in this VM by standing rule).

## Decisions D1 to D14

- D1 Ki technique damage family: YES. All 6 Ki damage sites convert to
  DbaDamage.ki, no new family. The factories already exist, so the foundation
  builds nothing here; A1 executes the swaps.
- D2 Mob voices: YES, implemented in this pass. Twelve synthesized voice
  events, ambient, hurt, and death for each of the four A3 species (soldier,
  warrior, robot, saibaman), generated by tools/gen_bespoke_sounds.py and
  wired in DbaSounds. A3 wires the getAmbientSound, getHurtSound, and
  getDeathSound call sites. Honest risk, carried from the audit: synthesized
  voices are the likeliest place in Scope 2 for a conversion to read worse
  than vanilla; the standard's revert-on-worse rule applies per family at
  Carter's PC test.
- D3 Mob ability damage: YES. FriezaSoldierEntity's ranged shot and
  SaibamanEntity's self-destruct convert from mobAttack to DbaDamage.ki in
  A3. Mob contact melee has no damageSources() call in mod code; it is
  vanilla Mob plumbing, the same exemption as the player's plain melee hit.
- D4 Frieza ranged attack shape: conversion only. The instant hit stays as
  it is in this scope; a real projectile is not required to convert it. The
  audit's Option A (reuse KiBlastEntity as the soldier's shot) stays
  available as a later change if Carter wants the shot to read as a
  projectile. No foundation work.
- D5 Otherworld cloud particles: YES, implemented in this pass. New
  CLOUD_PUFF particle type end to end (registration, client style, provider,
  generated texture, particle JSON). A6 wires the three call sites
  (OtherworldCloudParticleManager x2, YellowCloudBlock x1). The cloud entity
  alternative is rejected: the manager is already a particle system doing
  this job; the bespoke gap was only the particle type it feeds on.
- D6 Dimension effects: YES, with a mechanism correction that the record
  must carry. The audit and the brief name custom DimensionSpecialEffects
  classes registered client side. That class does not exist in Minecraft
  26.2 or 26.3: javap against both audit jars returns class not found, and
  DimensionType in both versions has no effects component at all (its
  components are the gameplay fields plus an EnvironmentAttributeMap). The
  "effects": "minecraft:overworld" line in the four dimension_type JSONs is
  dead data in these versions; the vanilla 26.2 dimension_type JSONs carry
  no effects field, and a dimension's sky, fog, water fog, and cloud colors
  live in its attributes map. The intent of D6 (the dimensions stop
  borrowing the overworld's look and get their own canon looks from the
  mod's own definitions) is therefore implemented the version-correct way:
  the dead effects line is removed from all four JSONs and each gains a
  mod-authored attributes map (values under Sound and texture additions
  below). No client classes exist to write and no registration API exists
  to call, so no client init or registration file was touched. Every
  gameplay field of the four JSONs is byte-identical; the diff per file is
  exactly the effects line out and the attributes block in. cloud_height is
  deliberately not set anywhere, so the mod's custom cloud layer stack is
  undisturbed. One caveat: the otherworld biome JSON already sets its own
  cloud_color (#E6FFE070) at biome level, which wins inside that biome;
  the dimension level pink cloud tint is the base look, and touching the
  biome value is A6 territory, not foundation.
- D7 Wish bank entries: YES, implemented in this pass. dragon_growl,
  dragon_flap, and wish_granted synthesized and wired; A2 swaps the call
  sites in DragonWishRitual, ShenronEntity, and PorungaEntity.
- D8 Menu sounds beyond the click: SKIP. No hover or select sounds exist
  today; adding them would be new design, not conversion. Only the existing
  click is converted (central fix 1 below).
- D9 DelayedDamageMixin source preservation: YES, implemented in this pass.
  See the combat fix section below.
- D10 Tail glyph particles: YES, implemented as particle types, because the
  code shape in TailHelper is particle spawns and particles are the honest
  fit. DAMAGE_SPARK replaces DAMAGE_INDICATOR pips and HAPPY_SPARKLE
  replaces HAPPY_VILLAGER hearts. A4 wires the TailHelper call sites.
- D11 Environmental damage lines: LEAVE both vanilla, listed here.
  PlanetDimension's drown() hazard tick (4.0) has no fitting bespoke family,
  and GravityTrainingBlockEntity's generic() is training-system pressure
  damage, the same game-system category as the MobPhysics generic() fall
  and stagger damage the audit recommends leaving. Neither is presentation.
  Because of this decision, GravityTrainingBlockEntity is NOT among the
  central fixes.
- D12 OtherworldGuide texture: YES, implemented in this pass. See below.
  A3 does the one-line renderer swap.
- D13 Small bank entries: YES, implemented in this pass. radar_blip,
  level_up, equip, and repair synthesized and wired. Transform needed no

  sites, so A4 wires it for form activation as is.
- D14 Damage type tags: context only. They were approved and landed
  separately as commit 8058771, the HEAD this foundation sits on. Not part

## The D9 combat fix (mixin/DelayedDamageMixin.java)

This is a behavior fix to a shared combat system, recorded as such, not a
line swap. Before: every player-attributed hit buffered by the mixin was
re-applied at the pop under a rebuilt playerAttack (or generic) source, so
the bespoke damage type of every delayed ability hit was silently
flattened, losing its death message, armor behavior, and the damage type
tag parity the tags commit just added. Now: the mixin also stores the
source of the largest single buffered hit (two new @Unique fields,
dba$dominantSource and dba$dominantAmount), and the pop applies the total
under that stored source when its causing entity is still present and
alive, which by construction is always a player, since only
player-attributed hits are buffered. The old rebuild remains as the
fallback in the same order (stored source, then playerAttack by UUID,
then generic), and both new fields reset with the existing ones.
Everything else is byte-identical: accumulation, the 10 tick window and
its cinematic-lock refresh, the drain branches, the hurt animation and
markHurt calls, and the KiBarrier deferred-damage flag handling. One
accepted subtlety: the stored source's direct entity may have despawned
by pop time (a spent ki blast, for example); vanilla damage sources
tolerate dead direct entities, and the armor and tag behavior still comes
from the stored type, which is the point of the fix.
